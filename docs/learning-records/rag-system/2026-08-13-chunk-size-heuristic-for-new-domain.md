## 정리한 답변

실험 전에 후보를 좁히는 휴리스틱이 있다.

1. **도메인의 자연스러운 단위에 맞춘다** — 문단 단위 문서(법률/재무)는 문단 하나 분량, 코드는 함수/클래스 단위(LlamaIndex `CodeSplitter` 등 언어별 스플리터), 표는 행이 안 잘리게.
2. **임베딩 모델의 실용 구간을 기본값으로** — OpenAI 계열은 대략 200~500토큰에서 잘 동작하고 800~1000을 넘으면 검색 정밀도가 떨어지는 경향이 흔히 보고된다(**설계 해석**, 모델·도메인마다 다를 수 있음).
3. **컨텍스트 예산을 역산** — `similarity_top_k × chunk_size`가 시스템프롬프트·대화이력을 뺀 LLM 컨텍스트 안에 여유 있게 들어가는지 계산한다.
4. **overlap은 chunk_size의 10~20%**를 시작값으로 잡는다.

다만 최종 검증은 실험이다. 위 휴리스틱으로 후보 2~3개(예: 256/512/1024)를 좁힌 뒤, 실제 Q&A 평가셋으로 검색 hit-rate와 답변 정확도를 비교해 확정하는 것이 실무 관행이다(**추천**). "실험만이 유일한 방법"은 아니지만 "실험 없이 확정"도 아니다.

## 재사용 가능한 판단 규칙

새 도메인을 맡을 때마다 무작위로 청크 사이즈를 실험하지 않는다. 자연스러운 단위·임베딩 모델 실용 구간·컨텍스트 예산으로 먼저 후보를 2~3개로 좁힌 뒤, 그 좁힌 후보만 실제 평가셋으로 비교한다. 이 순서는 [law-rag 로드맵 1블록 점검](2026-08-11-law-rag-roadmap-block-1-review.md)의 실험 A~D에서 corpus·계층을 먼저 검증한 뒤 검색 기법을 평가한 순서와 같은 원칙이다.
